# 家賃相場 自動更新（前回調査から7日以上経過していたら実行）

このホストのスケジューラは「毎日」の粒度でしか起動できないため、このワーカーは**毎日 9:00 JST 頃に起動される**。曜日では判定しない。**「`area-candidates` コレクションの全レコードのうち、最後に調査した日がもっとも古いものが、現在から7日以上経過しているか」**で実行するかどうかを決める。これにより、月曜にPCが落ちていて起動できなかった週があっても、次に起動したタイミングで取りこぼしなく実行される。

**対象は固定リストではなく、コレクションの全レコード。** 新しいエリア候補が追加されたら、次回の実行から自動的に更新対象に含まれる（テンプレート側の修正は不要）。

**家賃は上書きしない。** 毎回 `rentHistory`（履歴テーブル）に新しい行を追記していく方式。`rentRoomOnly` / `rentWithKitchen` / `rentSource` / `rentSurveyDate` / `rentStatus` は「最新値のミラー」として維持し続ける（比較ダッシュボードの上部表示が参照しているため）が、履歴を消すことは絶対にしない。

## 手順

### 0. 経過日数ガード（最初に必ず実行）

1. `manageCollection` の `getItems`（slug: `area-candidates`, **`ids` は指定しない**＝コレクションの全レコードを対象にする, fields: `id, stationName, wardName, rentSurveyDate, rentHistory`）で現在値を読む。レコードが0件なら何もせず終了する。
2. 各レコードについて「最終調査日」を決める。優先順は次の通り。
   - `rentHistory` に1件以上あれば、その**最後の行**の `date`
   - `rentHistory` が空なら `rentSurveyDate`
   - どちらも空、またはどちらも日付として解釈できない場合（例: `2026年7月` のような月まりの表記）は、**安全側に倒して「7日以上経過している」とみなす**（＝実行する）。日付の厳密なパースに失敗したことを理由に更新をスキップしない。
3. **全レコード**の「最終調査日」のうち**もっとも古い日付**を基準日とする（1つでも古いレコードがあれば全体を実行対象とする — 過去にWeb検索失敗で1件だけ取りこぼした場合でも、それを含めて再挑戦できるようにするため。新規追加されたばかりのレコードは調査履歴が無いので、それ自体が「7日以上経過」扱いとなり、次の実行を自動的にトリガーする）。
4. 現在の日本時間（Asia/Tokyo）の日付と基準日の差が **7日未満なら、レコードを一切変更せずここで処理を終了する。** 7日以上（同日を含め7日以上経過、境界は「7日以上」＝ `>= 7`）であれば、以下の手順に進む。

### 1. 対象

`area-candidates` コレクションの**全レコード**。手順0で取得したレコード一覧（`id` / `stationName` / `wardName`）をそのまま使う。固定リストは持たない — エリア候補が追加・削除されれば、次回の実行に自動的に反映される。1レコードあたりの手順（3〜5）を、取得した全件についてループして実行する。

### 2. 現在値の取得と比較基準

手順0で取得済みの `rentHistory` をそのまま使う（再度 `getItems` する必要はない。ただし `rentRoomOnly` / `rentWithKitchen` / `rentSource` / `rentStatus` / `notes` は手順0のfields指定に含めていないため、書き込み前に改めて `getItems` で取得しておく）。`rentHistory` は必ずそのまま保持し、新しい行を末尾に追加する（既存の行を削除・上書きしない）。

比較の基準値（直前値）は次の優先順で決める。

1. `rentHistory` に1件以上あれば、その**最後の行**（もっとも新しい行）の `roomOnly` / `withKitchen`
2. `rentHistory` が空なら、現在の `rentRoomOnly` / `rentWithKitchen`（この場合、比較の前に、現在値を日付 `rentSurveyDate`（無ければ「調査時点不明」）で `rentHistory` に1行追加してから、新しい調査結果をさらに追記する＝初回だけ2行増える）

### 3. 相場を調べる

対象の各レコード（駅）について、1R（ワンルーム）と1K の家賃相場を Web検索で調べる（SUUMO・CHINTAI・ホームズ・ニフティ不動産などの賃貸相場ページを情報源とする。検索クエリには `stationName` / `wardName` を使う）。範囲がある場合は「6.4〜6.6万円」のような幅表記のまま記録してよい。

### 4. 変化のチェック（2つの基準、それぞれ比較可否チェック付き）

1Rと1Kはそれぞれ独立に判定する。**2つの基準（直前比・初回調査比）はどちらも判定し、該当すればそれぞれ記録する（どちらか一方だけではない）。** ただし、それぞれの比較を行う前に必ず**比較可否チェック**を行う。数値の変化率を計算するのは「比較可能」と判定できたときだけで、それ以外は変化率を計算せず、代わりに「比較できなかった理由」を `notes` に記録する。

#### 比較可否チェック（各基準ごとに、比較相手ごとに実施）

基準1は「直前値」（`rentHistory` の最後の行）、基準2は「初回値」（`rentHistory` の最初の行）を比較相手とする。それぞれの比較相手について、以下の順でチェックする。

1. **出典が一致しているか** — 比較相手の行の `source` と、今回の `rentSource` を比較する。**完全一致でなければ**、その基準の数値比較（1R・1Kとも）をスキップし、`notes` に1行追記する。

   ```
   【基準変更】出典がSUUMO→ニフティ不動産に変わったため、直前値との比較は行いません
   ```

   （基準2＝初回値との比較の場合は「直前値」を「初回値」に置き換える。出典の書式は `<比較相手の出典>→<今回の出典>`。）

2. **値がレンジ表記でないか** — 出典が一致している場合のみ、1R・1Kそれぞれについて、比較相手の値・今回の値のいずれかが「6.4〜6.6万円」のようなレンジ表記であれば、**その項目（1RまたはK）だけ**数値比較をスキップし、`notes` に1行追記する。

   ```
   【基準変更】前回値がレンジのため比較不可
   ```

   （基準2の場合は「前回値」を「初回値」に置き換える。1Rと1Kの両方がレンジなら、項目ごとに1行ずつ記録してよい。）

3. 出典が一致し、値も両方とも単一値（レンジでない）の場合のみ、次のパーセンテージ判定に進む。

#### 基準1: 直前比 ±5%

比較可否チェックを通過した項目についてのみ、新しい値と「直前値」を比較する。**±5% 以上動いていた場合**、`notes`（総合メモ）に1行追記する（既存のnotesは消さず、末尾に追記）。例:

```
【家賃相場変動 2026-08-10】1R 7.96万円→8.5万円（+6.8%）。出典: SUUMO
```

#### 基準2: 初回調査比 ±10%（累積変動）

比較可否チェックを通過した項目についてのみ、新しい値と「初回値」（`rentHistory` の最初の行）を比較する。**±10% 以上動いていた場合**、`notes` に1行追記する。書式は基準1と区別できるよう「【家賃相場 累積変動】」ラベルを使い、変化率に「初回調査比」、期間に「調査期間 開始日〜終了日（＝今回の調査日）」を明記する。例（ユーザー指定の書式）:

```
【家賃相場 累積変動】1R 7.96万円→8.8万円（初回調査比+10.6%、調査期間 2026-08-01〜2026-10-05）
```

- 開始日は `rentHistory` 最初の行の `date`、終了日は今回の調査日（実行日）。
- **`rentHistory` の件数が今回追記する前でちょうど1件（＝最初の行＝直前値と同一エントリ）の場合、基準2は基準1と全く同じ比較になり重複するため、基準2の追記（比較可否チェックの結果も含む）はスキップしてよい**（基準1の記録だけで十分）。`rentHistory` が2件以上ある状態で初めて基準2の意味が出る。

いずれにも該当しない・記録すべき事象がない場合は notes への追記は不要。複数の事象（比較不可の通知、±5%変動、±10%累積変動）が同時に発生した場合はすべて追記する（順序: 比較可否の通知 → 基準1 → 基準2）。

### 5. 書き込み（履歴に追記 + 最新値ミラーの更新）

`manageCollection` の `putItems`（`mode: "merge"`）で、id ごとに以下を更新する。

- `rentHistory` — **既存の配列 + 今回の新しい行**（`{ date: "実行日（例: 2026-08-10）", roomOnly: "...", withKitchen: "...", source: "..." }`）を渡す。**既存の行を削除・変更しないこと**（履歴は増える一方でよい。件数上限は設けない）。
- `rentRoomOnly` / `rentWithKitchen` — 今回調べた最新値で更新（「最新値ミラー」）。
- `rentSource`（例: `SUUMO`、複数参照した場合は列挙）
- `rentSurveyDate`（実行日。例: `2026-08-10`）
- `rentStatus`（実在の掲載情報に基づく値が取得できれば `✅ 確定`、掲載が見つからず推測になった場合は `⚠️ 推定`）
- `notes`（4. で記録すべき事象（比較不可の通知／±5%変動／±10%累積変動）が1つ以上あった場合のみ、既存メモに追記した全文を渡す。事象が複数あれば全行追記。何も無ければ `notes` はそもそも row に含めない＝上書きしない）

### 6. 絶対に変更してはいけないフィールド

以下は今回の自動更新の対象外。`putItems` の row に**含めないこと**（誤って空文字や古い値を書くと上書き事故になる）。

- `lastTrainDepartTime` / `lastTrainArriveTime` / `lastTrainFareYen` / `firstTrainTime`
- `commuteSource` / `commuteSurveyDate` / `commuteStatus`
- `taxiFareEstimate` / `taxiFareSource` / `taxiFareSurveyDate` / `taxiFareStatus`
- `safetyScore` / `floodRisk` / `shelterWalkMinutes` / `supermarket24hCount` / `weekdayClinicCount`
- `goodReputation` / `complaints`
- `morningNote` / `morningPhoto` / `noonNote` / `noonPhoto` / `nightNote` / `nightPhoto` / `midnightNote` / `midnightPhoto`
- `wardName` / `stationName` / `lines` / `commuteMinutes` / `transfers`

### 7. 終了

対象の全レコードを処理したら、レコードを編集して静かに終了する。何も提示（present）しない。Webサーチが失敗した駅があれば、その駅は更新をスキップ（`rentHistory` にも行を追加しない）し、`notes` に「〇年〇月〇日: 相場情報の取得に失敗（要手動確認）」と追記する。1件あたりの処理が失敗しても、他のレコードの処理は続行すること（1件の失敗で全体を止めない）。
